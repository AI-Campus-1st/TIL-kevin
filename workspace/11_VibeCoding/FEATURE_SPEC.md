# Feature Specification

## 1. 구현 범위

### MVP

- 외부 URL 기반 레시피 저장 및 구조화
- 주간 식단 생성 및 날짜별 메뉴 변경
- 식단 확정 및 통합 장보기 목록 생성
- 장보기 목록의 보유 재료 제외·구매량 조정
- 대체 재료 제안 및 식단/장보기 목록 동기화
- 쿠팡 재료 검색 링크
- 오늘의 메뉴, 레시피 상세, 요리 완료 표시
- 선택적 평가·메모를 위한 데이터 구조와 기본 입력

## 2. 주요 사용자 흐름

### FLOW-01. 레시피 저장 → 주간 식단 생성 → 수정 → 확정

1. 사용자가 외부 레시피 URL을 입력한다.
2. 서버가 페이지 본문을 추출하고 AI가 구조화된 초안을 만든다.
3. 사용자는 추출된 레시피명·인분·재료량·조리 순서·시간을 검토하고 저장한다.
4. 사용자가 이번 주 식단 생성 화면에서 요리할 날짜를 선택한다.
5. 날짜별 기본 조리 가능 시간(평일 30분, 주말 70분)과 기본 인원 1명이 표시된다. 사용자는 필요한 값만 바꾼다.
6. 시스템은 사용자가 저장한 레시피만 후보로 삼아 날짜별 메뉴 초안을 만든다.
7. 사용자가 특정 날짜의 메뉴와 변경 요청사항을 입력해 해당 날짜의 후보만 다시 생성한다.
8. 다른 날짜의 메뉴 ID·설정·완료 상태는 변경되지 않아야 한다.
9. 사용자가 식단을 확정한다. 시스템은 메뉴에 포함된 재료를 인분에 맞게 계산해 장보기 목록을 생성한다.

### FLOW-02. 장보기 → 보유 재료 제외 → 대체품 적용 → 쿠팡 검색

1. 사용자가 확정 식단의 장보기 목록을 연다.
2. 목록에서 재료별 필요량과 출처 메뉴를 확인한다.
3. 사용자가 냉장고를 확인하고 이미 보유한 재료를 `보유함`으로 표시하거나 구매 수량을 직접 조정한다. 재고를 별도 테이블로 추적하지 않는다.
4. 사용자가 부족한 재료의 `대체 재료 보기`를 선택한다.
5. 시스템은 현재 레시피에서 사용 가능한 대체품 1~2개, 맛 차이, 필요량, 조리 방법 변경 여부를 표시한다.
6. 사용자가 특정 대체품을 선택하면 해당 레시피의 재료 관계를 바꾸고 장보기 목록을 다시 계산한다.
7. 동일 재료가 다른 날짜/레시피에서도 사용된다면, 변경한 레시피에 연결된 사용량만 제거한다. 다른 레시피의 필요량까지 삭제하면 안 된다.
8. 재료 행의 쿠팡 검색 링크를 열어 구매는 사용자가 직접 진행한다.

### FLOW-03. 오늘의 메뉴 → 요리 → 완료 → 선택적 회고

1. 사용자가 오늘 날짜에 확정된 메뉴를 확인한다.
2. 메뉴를 선택해 재료·수량·조리 순서·예상 시간·곁들임 메뉴를 확인한다.
3. 조리 과정에서 평가나 메모 입력을 강제하지 않는다.
4. 사용자가 한 번의 행동으로 `요리 완료`를 표시한다. 완료 시간과 해당 식단 메뉴를 저장한다.
5. 완료 직후 또는 나중에 사용자가 선택적으로 별점과 메모를 남긴다.
6. 해당 레시피를 다시 열었을 때 이전 평가/메모를 볼 수 있다. 기록이 없더라도 메뉴 확인 및 요리 완료 기능은 정상 동작해야 한다.

## 3. 기능별 명세

## F-01. 외부 URL 기반 레시피 아카이빙 (P0)

### 목적
저장한 레시피를 반복해서 원문에서 확인하지 않고 식단 구성과 조리에 재사용할 수 있도록 구조화한다.

### 입력
- 사용자가 제공한 URL
- 추출 결과에 대해 사용자가 직접 수정한 필드

### 처리
1. URL 형식 및 허용 프로토콜을 검증한다.
2. 동일 사용자가 동일 URL을 이미 저장했는지 확인한다. 중복 발견 시 기존 레시피 열기 또는 새로 저장 중 하나를 안내한다.
3. 서버에서 HTML을 가져오고 본문 텍스트를 추출한다.
4. AI가 아래 레시피 데이터 계약에 맞춰 추출한다.
5. 결과를 Zod로 검증한다. 누락/불확실 필드는 `확인 필요`로 표시한다.
6. 사용자가 정보를 검토하고 저장을 확정한 뒤에만 정식 레시피로 등록한다.
7. 본문 추출 실패, 접근 차단, 이미지/영상 위주 콘텐츠, AI 실패 시 원본 URL을 유지하고 수동 입력 또는 재시도를 안내한다.

### 화면 동작
- `URL 저장` → `가져오는 중` → `검토 필요` 또는 `실패` 상태를 명확히 보여준다.
- `저장`은 필수 필드가 유효할 때만 활성화한다. 레시피를 완전하게 추출하지 못한 경우 사용자가 수정해서 저장할 수 있다.
- 조리 시간·인분·재료 수량을 확실히 알 수 없으면 임의의 숫자를 만들어내지 않고 `미확인`으로 표시한다.

### 완료 기준
- 정상 URL의 추출 결과를 사용자가 검토·수정·저장할 수 있다.
- 실패 시 앱이 중단되지 않고 원인 및 재시도/수동 입력 경로를 제공한다.
- 페이지 본문에 포함된 프롬프트형 문자열은 데이터로 취급하며 시스템 지시로 실행하지 않는다.

## F-02. 주간 식단 생성 (P0)

### 입력 및 기본값
- 요리할 날짜: 사용자가 선택
- 평일 조리 가능 시간: 기본 30분
- 주말 조리 가능 시간: 기본 70분
- 식사 인원: 기본 1명
- 메뉴 후보: 사용자가 저장한 레시피

### 처리 규칙
1. 선택하지 않은 날짜에는 메뉴를 배정하지 않는다.
2. 날짜별로 해당 날짜의 시간 한도와 맞는 레시피를 우선한다. 초과하는 레시피는 기본적으로 제외하거나 낮은 우선순위로 처리한다. 정확한 규칙은 Q-06에서 확정한다.
3. 추천 카드에 레시피명, 예상 조리 시간, 주요 재료를 표시한다.
4. 각 식단 날짜는 핵심 요리 1개를 기본으로 한다. 곁들임은 있을 경우 별도 항목으로 표시한다. 곁들임 추천 수와 자동 배정 범위는 Q-07에서 확정한다.
5. 후보 부족 시 부족한 날짜와 이유를 알린다. 저장하지 않은 외부 레시피를 자동으로 섞지 않는다. 외부 레시피 추천은 별도 사용자 동의를 받은 다음 단계로 둔다.
6. 식단은 우선 `draft` 상태로 생성되며 사용자가 확정하기 전까지 확정 장보기 목록을 만들지 않는다.

### 생성 실패/빈 상태
- 저장 레시피가 0개: 레시피 등록 CTA와 URL 저장 화면 진입을 제공한다.
- 후보 부족: 가능한 날짜만 생성하고 미배정 날짜를 명시하거나, 전체 생성을 중단하고 선택지를 주는 정책을 Q-06에서 확정한다.
- AI/API 오류: 재시도 버튼을 제공하고 기존 초안이 있다면 덮어쓰지 않는다.

### 완료 기준
- 기본값으로 별도 설정이 없어도 식단 생성 요청을 시작할 수 있다.
- 각 추천은 저장 레시피 ID와 연결된다.
- 반환된 레시피 ID가 실제 사용자 소유 레시피가 아닌 경우 결과를 폐기한다.

## F-03. 날짜별 메뉴 변경 (P0)

### 입력
- 변경할 날짜 및 메뉴 항목 ID
- 자연어 변경 요청(선택 사항이 아닌 기본 입력)
- 선택적 조리 시간/재료 제약(기존 사용자가 요청한 문장으로 표현 가능)

### 처리 규칙
1. 변경 대상 날짜/메뉴만 재추천한다.
2. 변경 요청을 후보 필터링·정렬에 반영한다. AI가 임의의 새 레시피를 만들지 않고 저장 레시피 ID 중에서 추천한다.
3. 변경 전후에 다른 날짜의 식단 항목 ID, 메뉴, 시간, 상태가 보존되어야 한다.
4. 사용자가 새 후보를 선택하기 전에는 기존 메뉴를 유지한다.
5. 메뉴 변경이 확정되면 해당 식단 메뉴와 이후 장보기 목록 계산 입력을 함께 갱신한다.
6. 확정 식단을 변경한 경우 장보기 목록의 재계산 시점과 사용자 수정값 보존 정책은 Q-10에서 확정한다.

### 완료 기준
- 날짜 A의 메뉴 변경으로 날짜 B의 메뉴가 바뀌지 않는다.
- 변경 요청이 저장된 레시피 후보로 해결되지 않으면 가능한 후보가 없다는 안내를 보여준다.
- 사용자가 최종 적용하기 전까지 기존 메뉴를 보존한다.

## F-04. 식단 확정 및 통합 장보기 목록 (P0)

### 데이터 원칙
- 하나의 장보기 목록은 확정된 식단 버전과 연결한다.
- 각 장보기 항목은 통합 총량뿐 아니라 어떤 레시피/메뉴에서 사용되는지 출처 관계를 보존한다.
- 재료의 합산은 정규화 재료명과 호환 가능한 단위를 기준으로 한다.

### 재료 수량 계산
1. 기본 필요량 = 레시피 기준 수량 × (계획 인분 ÷ 레시피 기준 인분).
2. 동일 재료는 가능한 경우 묶되, 질량·부피·개수 등 호환되지 않는 단위를 무조건 합산하지 않는다.
3. 안전하게 환산할 수 없는 단위(예: `한 줌`, `적당량`, `1팩`)는 원문 단위를 보존하고 별도 행으로 둔다. 변환 규칙이 명확하지 않으면 임의 환산 금지.
4. 같은 재료라도 단위가 다르면 변환 규칙이 등록된 경우에만 합산한다. 단위 변환 규칙의 초기 범위는 Q-08에서 확정한다.
5. 사용자에게 `필요량`과 사용자가 수정하는 `구매 수량`을 별도로 표시한다.
6. 사용자가 보유한 재료는 `보유함`으로 표시해 구매 필요량 집계에서 제외한다. 재고 숫자를 장기 저장하거나 냉장고 재고를 관리하지 않는다.
7. 사용자가 장보기 목록의 수량을 수정하면 해당 수정 값을 저장한다.

### 목록 항목의 최소 필드
- 정규화 재료명 및 표시 이름
- 원문 재료명(레시피별 사용량 상세에서 확인 가능)
- 통합 필요량 및 단위
- 구매 수량 및 단위
- `already_owned` 여부
- `purchased` 여부를 구현할지 여부는 Q-09에서 확정
- 포함된 레시피/메뉴별 수량 내역
- 대체 재료 적용 내역
- 쿠팡 검색 링크

### 장보기 목록 그룹
Scenario에는 목록이 `구매 시점에 따라 구분`된다고 정의되어 있으나 그룹 기준은 미정이다. 화면 구현 전에 Q-09를 확정한다. 결정 전에는 임의로 `냉장/상온`, `당일/미리` 같은 범주를 만들어내지 않는다.

### 완료 기준
- 같은 정규화 재료·호환 단위의 사용량은 하나의 항목으로 합산한다.
- 보유 표시 및 구매 수량 변경 사항은 새로고침 후에도 보존된다.
- 모든 통합 항목에서 사용 레시피별 수량 상세를 확인할 수 있다.

## F-05. 대체 재료 제안 및 동기화 (P0)

### 입력
- 대체할 기준 재료
- 현재 사용되는 레시피 메뉴 항목

### 처리 규칙
1. 특정 재료를 사용하는 모든 레시피에 전역 적용하지 않는다. 대체 재료는 사용자가 선택한 레시피/메뉴의 재료 관계에만 적용한다.
2. 해당 레시피에 실제로 적용 가능한 후보 1~2개를 제안한다.
3. 후보별로 다음 정보를 제공한다: 대체 재료명, 필요한 양/비율, 맛 차이, 조리법이나 순서 변경 필요 여부, 주의사항 및 불확실성.
4. 레시피별 대체 가능성을 판단할 충분한 정보가 없으면 `확인 필요`로 표시하고 확정된 대체처럼 표현하지 않는다.
5. 사용자가 대체품을 선택하면 관련 레시피의 재료 관계를 갱신한다.
6. 장보기 목록은 레시피별 사용량 관계를 기준으로 다시 집계한다. 기존 재료를 사용하는 다른 레시피가 남아 있다면 해당 재료의 나머지 사용량을 유지한다.
7. 대체품 수량·단위가 확정되지 않으면 장보기 목록에 불확실한 숫자를 기록하지 않고 사용자 확인을 요청한다.
8. 조리 방법 변경이 필요한 경우 레시피의 원문 단계와 구분해 `대체 시 조리 안내`로 표시한다. 원문 조리 순서를 조용히 덮어쓰지 않는다.

### 완료 기준
- 한 메뉴의 대체 재료 선택이 다른 메뉴에 자동으로 적용되지 않는다.
- 선택 후 레시피와 장보기 목록이 한 번의 사용자 동작으로 동기화된다.
- 동기화 실패 시 일부 데이터만 바뀐 상태가 남지 않도록 트랜잭션 또는 안전한 재시도 처리를 구현한다.

## F-06. 쿠팡 재료 검색 (P0)

- 재료명으로 쿠팡 검색 URL을 구성하고 사용자가 클릭하면 새 탭으로 연다.
- 대체품이 적용된 경우 장보기 목록의 현재 구매 대상 재료명으로 검색한다.
- 상품 선택, 가격 수집, 장바구니 추가, 주문 금액 계산, 주문은 구현하지 않는다.
- 검색 URL은 한글·공백 등 특수 문자를 URL 인코딩한다.
- 검색 페이지 URL 형식이 변경될 수 있으므로 URL 생성 로직을 `buildCoupangSearchUrl(query)` 같은 단일 유틸리티로 격리한다.

## F-07. 오늘의 메뉴 및 조리 화면 (P0)

### 오늘 화면
- 한국 시간대 기준 오늘 날짜를 표시한다(시간대 확정은 Q-15).
- 오늘 확정된 메뉴가 있으면 레시피명·예상 시간·주요 재료를 표시한다.
- 메뉴가 없으면 빈 상태를 표시하고 주간 식단으로 이동할 수 있게 한다.
- 메뉴를 선택하면 레시피 상세 화면으로 이동한다.

### 레시피 상세/조리 화면
- 재료명, 인분에 따른 수량, 조리 순서, 예상 조리 시간, 곁들임 레시피를 표시한다.
- 조리 중에 별점/메모를 강제하지 않는다.
- `요리 완료` 버튼은 한 번의 사용자 동작으로 완료 상태와 완료 시각을 저장한다.
- 완료 상태는 해당 식단 날짜의 메뉴 항목에 연결한다. 같은 레시피를 다른 날짜에 요리해도 이력을 분리할 수 있어야 한다.
- 중복 클릭 요청은 중복 로그를 만들지 않고 동일 완료 상태로 처리한다.

## F-08. 선택적 요리 평가 및 메모 (P0 최소 저장 / P1 탐색 확장)

- 요리 완료는 평가 입력 여부와 무관하게 저장한다.
- 별점과 메모는 선택 사항이다.
- 별점 범위는 제품 결정 전까지 UI에 고정하지 않는다(Q-12). 권장안은 1~5점과 자유 메모다.
- 평가/메모는 레시피 ID와 해당 요리 이력 ID에 연결한다.
- 같은 레시피를 다시 선택했을 때 이전 기록을 보여준다. 이전 기록이 없으면 기록 영역을 숨기거나 빈 상태로 표시한다.
- `개선 항목`을 체크리스트로 별도 구조화할지는 미결정이며, 초기에는 자유 메모만으로 시작하는 방안을 권장한다(Q-12).

## F-09. 주간·월간 식단 탐색 (P1)

### 주간 식단
- 날짜별 메뉴, 예상 조리 시간, 주요 재료를 확인한다.
- 메뉴 선택 시 레시피 상세로 이동할 수 있다.
- 메뉴 변경을 바로 시작할 수 있다.

### 월간 주차 스트립(Monthly Weekly Strip)
- 달력을 기본 UI로 사용하지 않고, 월을 주차 단위 블록으로 분할해 가로 한 줄 스트립으로 표시한다.
- 각 블록에는 해당 주의 시작일과 식단 구성 여부를 표시한다.
- 구성된 주와 비어 있는 주는 색상만으로 구분하지 않고 텍스트/도트/채움 등 보조 표시를 함께 제공한다.
- 주차 블록 선택 시 해당 주의 식단 상세로 이동한다.
- 월의 첫/마지막 주가 인접 월 날짜를 포함하는 방식과 주 시작 요일은 Q-05에서 확정한다.

## F-10. 레시피 분류 및 탐색 (P1)

- 저장 레시피 검색·정렬을 지원한다.
- 국, 찌개, 메인, 반찬, 간단 요리, 세트 메뉴 등의 카테고리 사용을 제안한다. 최종 카테고리 목록은 Q-13에서 확정한다.
- 조리 시간·재료·주방 도구 필터를 확장 기능으로 제공한다.
- 관련 레시피는 저장된 레시피 내에서만 탐색한다. 외부 레시피를 제공할지는 별도 동의 및 정책 확정이 필요하다.
