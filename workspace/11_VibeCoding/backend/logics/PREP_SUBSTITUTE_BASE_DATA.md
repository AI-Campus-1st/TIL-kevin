# [사전 작업] 대체 재료 베이스 데이터 구축

> 성격: 서비스 운영 전에 한 번 수행하는 데이터 준비 작업 (런타임 비즈니스 로직 아님)
> 결과: 재료별 대체 후보를 `ingredient_substitutes` 베이스 테이블에 적재 → 서비스는 요청 시 AI를 호출하지 않고 이 데이터를 조회
> 관련: `../DATA_STRUCTURE.md`, `./UNIT_CONVERSION.md`, `docs/product/FEATURE_SPEC.md` F-06

---

## 1. 목적

- 장보기의 `대체 관리`에서 보여줄 대체 후보(1~2개)를 미리 만들어 둔다.
- 요청마다 AI를 호출하지 않으므로 응답 속도·비용·결과 일관성이 확보되고, 사람이 검수한 데이터만 노출할 수 있다.

## 2. 작업 단계

```text
① 재료 목록 확정 → ② AI 일괄 생성 → ③ 자동 검증 → ④ 사람 검수 → ⑤ 적재 → ⑥ 갱신 운영
```

### ① 재료 목록 확정

- 운영 시작 시점에는 재료 마스터(`ingredients`)가 비어 있으므로 시드 재료 목록을 먼저 만든다.
- 대상: 한식 가정 요리에 자주 쓰이는 재료 (양념·장류, 채소, 육류·해산물, 가공식품 등)
- 재료명은 원문 표기 기준으로 독립 관리한다 ("마늘", "다진 마늘"은 각각 별도 재료)
- 결과물: `ingredients` 시드 파일 (`name`, `normalized_name`)

### ② AI 일괄 생성

- 재료 목록을 묶음(예: 50개) 단위로 LLM(LangChain)에 보내 재료별 대체 후보를 생성한다.
- 지시문
  - 한국 가정에서 구하기 쉬운 재료로 최대 2개
  - 대체가 적절하지 않으면 후보를 만들지 않음 (빈 결과 허용)
  - 필요량 비율을 확신할 수 없으면 비율을 비워 둠
  - 맛 차이, 조리법 변경 필요 여부, 주의사항(알레르기·식감 등)을 함께 작성
- 구조화 출력 (재료당)

| 필드 | 설명 |
|---|---|
| `ingredientName` | 원래 재료명 |
| `candidates[].name` | 대체 재료명 |
| `candidates[].ratioLabel` | 비율 표기 (예: "버터 1 : 식용유 0.8") |
| `candidates[].factor` | 원래 수량에 곱할 배수, 불확실하면 `null` |
| `candidates[].unit` | 대체 재료의 단위 (원래 단위를 그대로 쓰면 `null`) |
| `candidates[].tasteDifference` | 맛 차이 |
| `candidates[].cookingChange` | 조리 변경 안내 (없으면 `null`) |
| `candidates[].caution` | 주의사항 (없으면 `null`) |

### ③ 자동 검증 (스크립트)

| 검증 | 처리 |
|---|---|
| 후보 수 0~2개 | 초과분 제거 |
| 대체 재료명이 원래 재료와 같음 | 후보 제거 |
| `factor`가 0 이하 또는 비정상적으로 큼 (예: 10 초과) | `factor = null` |
| `unit`이 단위 기준표에 없음 | `UNIT_CONVERSION.md` 별칭 사전으로 정규화, 실패 시 `null` |
| 원래 재료와 대체 재료의 단위 차원이 다른데 `factor`가 있음 | `factor = null` (차원 간 환산 금지) |
| `factor = null` | `uncertain = true` (사용자가 적용 시 확인 필요) |

### ④ 사람 검수

- 검수용 시트(CSV)로 내보내 담당자가 확인: 후보 적절성, 비율, 주의사항 문구
- 검수 상태: `approved` / `rejected` / `edited`
- `approved`·`edited`만 적재 대상

### ⑤ 적재

- 대체 재료명이 재료 마스터에 없으면 마스터에 먼저 추가한다.
- `ingredient_substitutes`에 적재 (재료당 우선순위 1~2)
- 시드 마이그레이션 또는 일회성 적재 스크립트로 수행하고, 같은 입력으로 다시 실행해도 중복이 생기지 않게 한다 (재료 ID + 대체 재료 ID 기준 upsert).

### ⑥ 갱신 운영

- 운영 중 레시피 분석으로 새 재료가 마스터에 추가되면, 그 재료는 다음 일괄 작업 전까지 대체 후보가 없다 (화면에서 `대체 관리` 미표시).
- 새로 추가된 재료(대체 데이터 미생성 재료)를 모아 ②~⑤를 주기적으로 반복한다. 실행 주기는 운영 정책으로 정한다.
- 생성에 사용한 모델·지시문 버전을 기록해 재생성 시 비교할 수 있게 한다.

## 3. 베이스 데이터 구조 (`ingredient_substitutes`)

| 필드 | 설명 |
|---|---|
| `id` | PK — 화면의 대체 후보 ID |
| `ingredient_id` | 원래 재료 (FK → `ingredients`) |
| `substitute_ingredient_id` | 대체 재료 (FK → `ingredients`) |
| `priority` | 1 또는 2 |
| `ratio_label`, `factor`, `unit_code` | 비율 표기, 배수(불확실 `null`), 단위 |
| `taste_difference`, `cooking_change`, `caution` | 안내 문구 |
| `uncertain` | `factor`가 없거나 단위를 확정하지 못한 경우 `true` |
| `source_version` | 생성 모델·지시문 버전 |

- 전 사용자 공용 데이터 (사용자는 읽기만)

## 4. 서비스에서의 사용 (참고)

- 대체 후보 조회: 장보기 항목의 재료 ID로 `ingredient_substitutes`를 조회해 우선순위 순으로 최대 2개 표시
- 대체 필요량: 레시피 기준 수량 × `factor` (결정론적 계산, `factor = null`이면 "확인 필요")
- 적용: 적용한 후보를 해당 식단·레시피 재료의 대체 기록(`ingredient_substitutions`)에 연결
- 런타임 AI 호출 없음

## 5. 검토 필요 사항

1. **시드 재료 목록 출처와 규모**: 직접 작성 vs 레시피 사이트 빈출 재료 기반, 초기 몇 개로 시작할지
2. **검수 담당과 기준**: 주의사항(알레르기 등) 문구의 최종 확인 책임
3. **갱신 주기**: 새 재료 대체 데이터 생성 배치의 실행 주기
