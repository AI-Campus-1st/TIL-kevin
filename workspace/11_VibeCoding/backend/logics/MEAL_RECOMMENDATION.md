# 자동 식단 추천

> 범위: 사용자의 저장 레시피 목록을 근거로 날짜별 주 레시피와 곁들임 레시피를 LLM(LangChain)으로 추천하는 로직
> 제외: API 엔드포인트·요청/응답·상태 코드 (API 명세에서 다룸), 장보기 목록 계산 (`../BUSINESS_LOGICS.md` §4.4)
> 관련: `../DATA_STRUCTURE.md`, `docs/product/FEATURE_SPEC.md` F-02·F-03·F-04
> 구현: `backend/app/domain/meal_planning.py`(후보 거르기·검증), `backend/app/services/meal_recommendation/` — `prompts.py`, `schemas.py`, `chains.py`, `service.py`

---

## 1. 목적과 원칙

- 사용자가 고른 날짜마다 조리 시간 조건에 맞는 **주 레시피 1개**와 어울리는 **곁들임 레시피**를 정한다.
- 후보는 사용자가 저장한 레시피로만 한정한다. LLM이 새 레시피를 만들거나 저장되지 않은 레시피를 넣지 않는다.
- 조건에 맞는 후보가 없거나 추천에 실패하면 임의로 채우지 않고 해당 날짜를 **식단 없는 상태**로 둔다.
- 후보 거르기(조건 판정)는 결정론적 코드, 후보 중 **선정과 조합**은 LLM이 맡는다.
- 추천이 진행 중인지, 날짜별로 어떻게 끝났는지 **상태를 저장**해 화면이 진행 상황을 보여주고 중복 실행을 막는다 (6장).

## 2. 전체 흐름

```text
[입력] 날짜별 { 날짜, 인분, 조리 시간 } (+ 변경 요청 코멘트)
   │
   ▼
[6. 상태 기록] 주간 생성 generating, 날짜별 pending
   │
   ▼
[3.1 후보 거르기] 결정론적 코드
   │  후보 없음 → 해당 날짜 실패
   ▼
[3.2 주 레시피 선정] LLM — 주간 단위 1회 호출
   │
   ▼
[3.3 결과 검증] 후보 밖 ID·조건 위반 → 해당 날짜 결과 폐기
   │
   ▼
[4. 곁들임 레시피 선정] 사용자 지정 관계 우선 → 부족하면 LLM
   │
   ▼
[5. 반영] 성공 날짜 확정 저장, 실패 날짜 식단 없음 + 장보기 재계산 (하나의 트랜잭션)
   │
   ▼
[6. 상태 기록] 날짜별 success / failed, 주간 생성 complete / partial / failed
```

---

## 3. 주 레시피 선정 (레시피 목록 반영)

### 3.1 후보 거르기 (결정론적)

날짜마다 아래 조건을 모두 만족하는 레시피만 후보로 둔다.

| 조건 | 기준 |
|---|---|
| 소유 | 요청 사용자의 레시피 |
| 상태 | `status = saved`, `is_delete = false` |
| 역할 | `category ≠ side` (곁들임 카테고리는 주 레시피 후보에서 제외) |
| 조리 시간 | `cook_minutes`가 확인되어 있고 날짜별 조리 시간 이하 (주 레시피만 확인, 곁들임 조리 시간은 합산하지 않음) |
| 재료 | 연결된 재료가 1개 이상 (장보기 계산 가능) |

- 날짜별 조리 시간 기본값: 평일 30분, 주말 70분 (요청값 우선)
- 후보가 0개인 날짜는 LLM에 보내지 않고 바로 실패 처리 (사유: "조리 시간 N분 이내의 저장 레시피가 없습니다" / "저장된 레시피가 없습니다")
- 날짜별 변경(재생성)은 현재 주 레시피를 후보에서 제외

### 3.2 LLM 선정

**호출 단위**
- 주간 생성은 선택된 날짜 전체를 **한 번에** 보내 한 주 안의 다양성을 LLM이 함께 판단하게 한다.
- 날짜별 변경은 대상 날짜 1개만 보내되, 같은 주의 다른 날짜 식단을 참고 정보로 함께 전달한다.

**LLM에 전달하는 정보** (필요한 최소 정보만)

| 구분 | 내용 |
|---|---|
| 날짜별 조건 | 날짜, 요일, 인분, 조리 시간, 해당 날짜의 후보 레시피 ID 목록 |
| 후보 레시피 요약 | ID, 레시피명, 카테고리, 조리 시간, 주요 재료명(상위 N개) |
| 조리 기록 요약 | 레시피별 최근 조리일, 평균 별점 (기록이 있는 경우만) |
| 같은 주 기존 식단 | 이미 확정된 날짜의 레시피 (선택되지 않은 날짜, 변경 시 다른 날짜) |
| 변경 요청 코멘트 | 날짜별 변경 시 사용자가 입력한 경우만 (신뢰할 수 없는 입력으로 구분해 전달) |

- 메모 원문 등 불필요한 사용자 데이터는 보내지 않는다.

**선정 기준 (지시문)**
1. 반드시 해당 날짜의 후보 ID 중에서만 고른다.
2. 한 주 안에서 같은 레시피 반복을 피한다. 후보 수가 날짜 수보다 적을 때만 반복을 허용하되 연속된 날짜에는 두지 않는다.
3. 카테고리와 주요 재료가 연달아 겹치지 않게 분산한다.
4. 최근에 조리한 레시피는 뒤로 미루고, 별점이 높은 레시피를 우선한다.
5. 변경 요청 코멘트가 있으면 이를 우선 반영한다. (예: "국물 요리" → soup 카테고리 우선, "간단하게" → 조리 시간 짧은 순)
6. 코멘트를 만족하는 후보가 없으면 기본 기준으로 고르고 그 사실을 사유에 적는다.

**구조화 출력 (`MealPlanSelection`)**

| 필드 | 설명 |
|---|---|
| `days[].date` | 날짜 |
| `days[].recipeId` | 선정한 주 레시피 ID (고를 수 없으면 `null`) |
| `days[].reason` | 선정 사유 한 문장 (로그·디버깅용, 화면 미노출) |

### 3.3 결과 검증

| 검증 | 실패 시 |
|---|---|
| `recipeId`가 해당 날짜 후보 목록에 있음 | 해당 날짜 결과 폐기 → 실패 |
| 응답에 요청한 날짜가 모두 있음 | 빠진 날짜 → 실패 |
| 같은 레시피 연속 배치 금지 | 뒤 날짜 결과 폐기 → 실패 |
| 스키마 불일치 | 1회 재요청 후에도 실패하면 전체 실패 |

- 실패한 날짜는 **식단 없는 상태**로 둔다 (5장).
- LLM 호출 자체가 실패(타임아웃·공급자 오류)하면 설정 횟수까지 재시도 후 **요청 전체 실패**로 처리한다. 결정론적 규칙으로 대신 채우지 않고, 기존 식단·장보기 목록은 변경하지 않는다 (`docs/design/pages/WEEKLY.md` 전체 실패 규칙).

## 4. 곁들임 레시피 선정

주 레시피가 확정된 날짜마다 수행한다.

### 4.1 후보 우선순위

| 순위 | 후보 | 비고 |
|---|---|---|
| 1 | 사용자 지정 곁들임 (`recipe_side_dishes`에서 주 레시피에 연결된 레시피) | 저장·미삭제 레시피만 |
| 2 | 저장 레시피 중 `category = side` 또는 `soup` | 1순위 후보가 없을 때만 LLM이 선택 |

### 4.2 선정 규칙

- 1순위 후보가 있으면 그중에서 고른다. 여러 개면 같은 주에 덜 쓰인 레시피를 우선한다 (결정론적).
- 1순위 후보가 없으면 2순위 후보 요약(ID, 이름, 카테고리, 주요 재료)과 주 레시피 정보를 LLM에 보내 어울리는 곁들임을 고르게 한다.
  - 지시문: 주 레시피와 재료·조리법이 겹치지 않고 함께 먹기 좋은 것, 어울리는 후보가 없으면 고르지 않음
  - 구조화 출력: `{ sideRecipeIds[], reason }`
- 날짜당 곁들임 수는 설정값(`MAX_SIDE_DISHES`, 기본 1)까지
- 곁들임의 조리 시간은 날짜별 조리 시간 조건에 넣지 않는다 (주 레시피만 확인)
- 결과 ID가 후보 목록에 없거나 주 레시피와 같으면 폐기
- 적절한 후보가 없으면 곁들임 없이 식단을 구성한다 (실패로 처리하지 않음)

### 4.3 저장

- 선정 결과는 해당 날짜 식단의 조합(`meal_plan_entry_sides`)으로만 저장한다.
- 사용자 지정 곁들임 관계(`recipe_side_dishes`)는 추천 과정에서 추가·삭제하지 않는다.

## 5. 반영

**주간 생성**
- 성공한 날짜: 식단 항목을 생성(또는 교체)하고 즉시 확정한다. 기존 식단을 교체하면 완료 상태·적용된 대체 재료를 초기화한다.
- 추천에 실패한 날짜(후보 없음·결과 폐기): **식단 없는 상태**로 둔다. 그 날짜에 기존 식단이 있었으면 제거하고, 화면에는 해당 날짜의 `식단 생성` 진입만 제공한다.
- 요청 전체 실패(LLM 호출 실패 등): 어떤 날짜도 변경하지 않는다.
- 선택하지 않은 날짜의 식단은 변경하지 않는다.

**날짜별 변경** (`FEATURE_SPEC.md` F-03)
- 성공 시 대상 날짜만 교체한다. 실패 시 기존 식단을 유지한다.

**공통**
- 식단 반영과 장보기 목록 재계산은 하나의 트랜잭션으로 처리한다.

## 6. 추천 진행 상태 관리

### 6.1 상태 저장 단위

| 단위 | 저장 위치 | 상태 |
|---|---|---|
| 주간 생성 1회 | `meal_plan_generations` (주당 최신 1건) | `generating` → `complete` / `partial` / `failed` |
| 날짜별 | `meal_plan_generation_days` | `pending` → `success` / `failed` (+ 실패 사유) |

- 날짜별 변경도 같은 방식으로 대상 날짜 1건짜리 생성 기록을 남긴다.

### 6.2 상태 전이

```text
요청 접수 ──▶ generating (날짜별 pending)
                │
                ├─ 날짜별 결과 확정 ──▶ success / failed
                │
                └─ 모든 날짜 종료 ──▶ 모두 success: complete
                                      일부 failed: partial
                                      모두 failed: failed
```

- 날짜별 결과는 추천이 끝나는 대로 기록해, 화면이 `생성 중` / `일부 생성 완료` / `전체 생성 완료` / `실패`를 표시할 수 있게 한다.
- 처리 중 서버가 중단되어 `generating`이 설정 시간(`GENERATION_TIMEOUT_SECONDS`)을 넘기면, 남은 `pending` 날짜를 `failed`(사유: 시간 초과)로 바꾸고 주간 상태를 다시 계산한다.

### 6.3 중복 실행 방지

- 같은 사용자·같은 주에 `generating` 상태가 있으면 새 생성·변경 요청을 받지 않는다.
- 상태 확인과 `generating` 기록은 하나의 트랜잭션(또는 행 잠금)으로 처리해 동시에 두 요청이 시작되지 않게 한다.

### 6.4 재시도

- 실패한 날짜는 식단 없는 상태이므로, 사용자가 해당 날짜만 다시 생성할 수 있다 (새 생성 기록).

## 7. 설정값

| 키 | 용도 |
|---|---|
| `LLM_PROVIDER`, `LLM_MODEL` | 추천에 사용할 모델 |
| `LLM_REASONING_EFFORT` | thinking effort (기본 `none`). `none`일 때만 `temperature=0` 적용 |
| `AI_TIMEOUT_SECONDS`, `AI_MAX_RETRIES` | 타임아웃·재시도 |
| `RECOMMEND_INGREDIENT_COUNT` | 후보 요약에 넣을 주요 재료 수 |
| `MAX_SIDE_DISHES` | 날짜당 곁들임 최대 수 (기본 1) |
| `DEFAULT_COOK_MINUTES_WEEKDAY` / `_WEEKEND` | 기본 조리 시간 30 / 70 |
| `GENERATION_TIMEOUT_SECONDS` | `generating` 상태 최대 유지 시간 |

## 8. 결정 사항

| 항목 | 결정 |
|---|---|
| 추천 실패 시 | 대체 로직 없음. 날짜별 추천 실패는 해당 날짜 식단 없음, 요청 전체 실패는 기존 데이터 유지 |
| 추천 진행 상태 | 주간·날짜별 상태 저장, 같은 주 중복 실행 방지 |
| 곁들임 조리 시간 | 조리 시간 조건은 주 레시피만 확인 |
| 카테고리 | 카테고리는 레시피 분류로만 관리한다. `set` 등 특정 카테고리에 곁들임 생략 같은 별도 추천 규칙을 두지 않는다 |
