# 수집 레시피 분석 (출처별)

> 범위: 사용자가 추가한 레시피 URL을 외부 서비스(Gemini API, YouTube Data API, LLM)로 분석해 레시피 데이터로 구조화하는 로직
> 제외: API 엔드포인트·요청/응답·상태 코드 (API 명세에서 다룸), URL 검증·중복 확인 (`../BUSINESS_LOGICS.md` §1)
> 관련: `../DATA_STRUCTURE.md`, `./UNIT_CONVERSION.md`, `docs/product/FEATURE_SPEC.md` F-01·F-04
> 구현: `backend/app/services/recipe_analysis/` — `prompts.py`(프롬프트), `schemas.py`(구조화 출력), `chains.py`(LangChain 호출), `postprocess.py`(분리·병합·검증), `pipeline.py`(출처별 흐름)

---

## 1. 목적

- 출처(유튜브, 블로그, 레시피 사이트)마다 다른 형태의 레시피 정보를 **하나의 레시피 구조**로 정리한다.
- 한 출처에 레시피가 여러 개 있으면 **각각 별도 레시피로 분리**하고, 레시피 사이의 주 요리·곁들임 관계를 분석해 곁들임 연결로 저장한다.
- 확인되지 않은 정보는 추정하지 않고 미확인으로 남겨, 사용자가 검토(`needs_review`) 단계에서 확인·수정하게 한다.
- **출처에 다시 접속해 분석하는 것은 레시피를 하나도 추출하지 못한 완전 실패 때뿐**이다. 레시피가 추출된 뒤의 수정 요청은 저장된 레시피 데이터만으로 처리한다 (9장).

## 2. 공통 처리 흐름

```text
[수집 작업 시작] (출처 단위 recipe_import_jobs 1건, 대표 레시피 1건 importing)
   │
   ├─ source_type = youtube ──▶ 3. 유튜브 분석 (Gemini → 댓글 보완)
   ├─ 10000recipe ───────────▶ 4.1 페이지 구조 파싱 → 부족분 LLM 구조화
   └─ naver_blog / web ──────▶ 4.2 본문 추출 → LLM 구조화
   │
   ▼
[5. 레시피 분리·곁들임 관계 분석] 레시피 N개 → 레시피별 저장 단위 + 주 요리/곁들임 관계
   │
   ▼
[6. 재료·단위 정리] 원문 수량 → 수량·단위 코드 (UNIT_CONVERSION.md)
   │
   ▼
[7. 결과 검증] 스키마 + 도메인 규칙
   │
   ▼
[8. 결과 반영] 최신 job이면 레시피 생성·갱신 + 곁들임 연결 → status = needs_review
```

수정 요청 흐름 (출처 접속 없음, 9.2)

```text
[수정 요청] 대상 레시피 1개 + 코멘트
   │
   ▼
[저장된 레시피 데이터 + 코멘트 → 기본 LLM 재정리]
   │
   ▼
[6. 재료·단위 정리] → [7. 결과 검증] → [대상 레시피만 갱신] → status = needs_review
```

### 2.1 공통 출력 구조 (내부 Pydantic 스키마)

분석 결과는 출처 하나에 대해 `recipes[]` 배열로 받는다 (레시피가 1개여도 배열).

| 필드 | 설명 | 미확인 처리 |
|---|---|---|
| `recipes[].title` | 레시피명 | 레시피가 1개이고 사용자가 입력한 이름이 있으면 우선, 없으면 추출값, 둘 다 없으면 `null` |
| `recipes[].category` | `soup` / `side` / `main` / `simple` / `set` | 판단 불가 시 `null` |
| `recipes[].role` | `main`(주 요리) / `side`(곁들임) / `unknown` | 판단 불가 시 `unknown` |
| `recipes[].sideOf[]` | 이 레시피가 곁들임으로 어울리는 주 요리의 배열 순번 | 관계가 없으면 빈 배열 |
| `recipes[].baseServings` | 기준 인분 | 명시된 경우만, 없으면 `null` |
| `recipes[].cookMinutes` | 예상 조리 시간(분) | 명시되지 않으면 `null` (영상 길이로 추정 금지) |
| `recipes[].ingredients[]` | `{ name, rawAmount }` — 재료명과 **원문 수량 표기** | 수량 없는 재료는 `rawAmount=null` |
| `recipes[].steps[]` | 조리 순서 문장 배열 | 없으면 빈 배열 |
| `recipes[].uncertainFields[]` | 확정하지 못한 필드 목록 | — |

- LLM은 수량을 숫자로 바꾸거나 단위를 환산하지 않는다. `"1숟갈"`, `"1/2컵"`, `"약간"`처럼 **원문 그대로** 추출하고, 숫자·단위 변환은 6단계의 결정론적 코드가 맡는다.
- 재료명은 원문 표기를 유지한다. "다진 마늘"을 "마늘"로 바꾸지 않는다 (`DATA_STRUCTURE.md` 결정 12).
- 여러 레시피가 같은 재료를 써도 레시피별로 따로 기록한다 (공통 양념을 한 레시피에 몰지 않음).

## 3. 유튜브: Gemini 영상 분석 (LangChain)

처리 순서: **① Gemini 영상 분석 → ② 댓글 확인 필요 여부 판단 → ③ YouTube Data API 댓글 분석 (필요 시)**

### 3.1 ① Gemini 영상 분석

**호출 방식**
- LangChain `ChatGoogleGenerativeAI`(`langchain-google-genai`)에 텍스트 지시문 + 유튜브 영상 URL을 멀티모달 입력으로 전달
- `with_structured_output(YoutubeRecipeAnalysis)`로 Pydantic 스키마에 맞춘 응답을 받음
- LangChain 통합이 유튜브 URL 입력을 지원하지 않는 버전이면, 같은 인터페이스를 구현한 `google-genai` SDK 어댑터로 교체 (`app/integrations/`에서 공급자 구현 분리)
- 모델명은 설정값 (`GEMINI_MODEL`, 실험 노트북 기준 `gemini-3.8-flash`)

**지시문에 담을 내용**
- 영상의 음성·화면 자막·화면 텍스트·영상 설명을 근거로 재료와 조리 순서를 한국어로 정리
- 재료 수량은 영상에서 말하거나 보여준 표현 그대로 기록 (계량 변환 금지)
- 영상에서 확인되지 않은 값은 비워 두고, 추측하지 않음
- 영상에 레시피가 여러 개면 **레시피별로 분리**하고, 각 레시피가 주 요리인지 곁들임인지와 어떤 주 요리에 곁들이는지 표시 (5장)
- 재료 또는 조리 순서 정보가 없거나 부족하면 그 사실을 표시 (일부 재료·수량만 빠진 경우도 "부족"에 포함, 댓글 보완 시 기존 값은 유지 §3.3)

**구조화 출력 (`YoutubeRecipeAnalysis`)**

| 필드 | 설명 |
|---|---|
| `recipes[]` | 2.1 공통 출력 구조 |
| `needsCommentCheck` | 어느 레시피든 재료 또는 조리 순서가 영상에 없거나 부족하면 `true` |
| `missingFields[]` | `{ recipeIndex, fields: ("ingredients" \| "steps")[] }` — 레시피별로 영상에서 확인하지 못한 항목 |

**실패 처리**

| 상황 | 처리 |
|---|---|
| 영상 없음·비공개·연령 제한 등 분석 불가 | 수집 실패, 사유 "영상을 분석할 수 없습니다" |
| 타임아웃·일시적 공급자 오류 | 설정된 횟수(`AI_MAX_RETRIES`)까지만 재시도 후 수집 실패, 사용자 재시도 가능 |
| 스키마에 맞지 않는 응답 | 1회 재요청 후에도 실패하면 수집 실패 |
| 레시피가 하나도 없음 (요리 영상이 아님) | 수집 실패, 사유 "레시피 정보를 찾지 못했습니다" |

### 3.2 ② 댓글 확인 필요 여부 판단

- `needsCommentCheck=false` → 댓글 조회 없이 5단계로 진행
- `needsCommentCheck=true` → ③ 실행
- 두 값은 해당 job의 `needs_comment_check`, `missing_fields`에 저장

### 3.3 ③ YouTube Data API 댓글 분석

**조회**
- `commentThreads.list`: `videoId`, `order=relevance`(인기순), `maxResults=3`, `textFormat=plainText`
- 최상위 댓글 본문만 사용 (답글 제외)

**분석 (LangChain, 기본 LLM 공급자)**
- 댓글 분석은 Gemini가 아닌 기본 LLM 공급자(`langchain-openai`)로 수행한다.
- 댓글 3개, 레시피명 목록, `missingFields`, 영상에서 얻은 재료(수량 포함, 수량이 없으면 "수량 없음" 표시)와 조리 단계 수를 함께 전달해 각 댓글에 어느 레시피의 누락 항목(재료·조리 순서)이 있는지 판단하고, 있으면 추출
- 재료는 목록에 없는 재료와 수량이 없는 재료의 수량만, 조리 순서는 영상에 조리 순서가 전혀 없을 때만 추출
- 구조화 출력: `{ items: [{ recipeIndex, ingredients[], steps[] }] }`

**병합 규칙**
- 영상에서 얻은 값은 덮어쓰거나 삭제하지 않는다. 레시피별 `missingFields`에 해당하는 항목만 보완한다.
  - 재료: 댓글의 재료 중 목록에 없는 재료는 뒤에 추가하고, 이미 있는 재료는 영상에 수량이 없을 때만 댓글 수량으로 채운다. 같은 재료 여부는 정규화한 재료명(공백 정리)으로 판단한다.
  - 조리 순서: 영상에 조리 단계가 하나도 없을 때만 댓글의 조리 순서를 사용한다. 기존 단계가 있으면 순서를 끼워 넣을 수 없으므로 유지한다.
- "부족"에는 재료가 아예 없는 경우뿐 아니라 일부 재료나 수량이 빠진 경우도 포함된다. 댓글이 다른 레시피의 정보로 잘못 판단되더라도 영상 데이터가 사라지지 않도록 하기 위한 규칙이다.
- 여러 댓글에 같은 정보가 있으면 인기순 상위 댓글을 우선 (이미 채운 수량은 다음 댓글로 바꾸지 않음)
- 댓글이 어느 레시피에 해당하는지 판단할 수 없으면 사용하지 않음
- 보완 후에도 해결되지 않은 누락 항목은 `uncertainFields`에 남긴다.
  - 재료: 모든 재료에 수량이 있으면 해결, 하나라도 수량이 없으면 미해결
  - 조리 순서: 비어 있던 조리 순서를 댓글로 채웠을 때만 해결 (기존 단계를 유지한 경우는 미해결)
- 댓글로 채운 항목도 사용자 검토 대상 (`needs_review`)

**예외**

| 상황 | 처리 |
|---|---|
| 댓글 비활성화 | 댓글 보완 없이 진행, 누락 항목은 `uncertainFields` |
| 댓글에 정보 없음 | 위와 동일 |
| 할당량 초과·API 오류 | 위와 동일 (수집 실패로 처리하지 않음) |

- 댓글 원문은 저장하지 않는다 (`DATA_STRUCTURE.md` 결정 8).

## 4. 웹페이지 출처

### 4.1 만개의레시피 (`10000recipe`)

**레시피 ID 추출 (중복 확인 기준)**

- 레시피 URL은 `https://www.10000recipe.com/recipe/7069580` 형태이며, 경로 맨 뒤의 숫자(`7069580`)를 **레시피 ID**로 사용한다.
- 정규표현식으로 형식을 확인하고 ID를 추출한다.

  ```text
  ^https?://(?:www\.|m\.)?10000recipe\.com/recipe/(\d+)/?(?:[?#].*)?$
  ```

  - 1번 캡처 그룹 = 레시피 ID
  - 스킴(`http`/`https`), `www.`·`m.`(모바일) 유무, 끝 `/`, 쿼리·프래그먼트 차이는 무시한다.
- 중복 확인은 URL 문자열이 아닌 **레시피 ID** 기준이다. 형식이 달라도 ID가 같으면 같은 레시피로 보고 `409 duplicate_recipe` + 기존 레시피로 응답하며, 페이지를 가져오거나 분석하지 않는다 (유튜브 `video_id`와 같은 방식, `../BUSINESS_LOGICS.md` §1.4).
- `normalized_url`은 ID로 다시 만든 `https://www.10000recipe.com/recipe/{id}`로 저장해 `(user_id, normalized_url)` 유니크 제약이 ID 기준으로 동작하게 한다 (`../DATA_STRUCTURE.md`).
- `10000recipe.com` 호스트이지만 정규표현식에 맞지 않는 URL(목록·검색·카테고리 페이지 등)은 레시피 페이지가 아니므로 수집 작업을 만들지 않고 `422 validation_error`로 응답한다.

**페이지 파싱**

- 레시피 페이지는 재료·조리 순서 영역이 정해진 구조라서 **HTML 파싱을 우선** 적용 (선택자는 구현 시 실제 페이지로 확인)
  - 레시피명, 인분, 조리 시간, 재료 목록(재료명 + 수량 표기), 조리 단계, 대표 이미지
- 페이지 하나는 레시피 1개로 보되, 재료 목록이 "주재료 / 양념 / 소스" 등 묶음으로 나뉘어 있어도 같은 레시피의 재료로 처리
- 파싱 결과에 빠진 항목이 있을 때만 본문 텍스트를 LLM 구조화(4.2와 같은 방식)로 보완
- 페이지 구조가 바뀌어 파싱이 실패하면 전체를 4.2 방식으로 처리

### 4.2 네이버 블로그 · 일반 웹페이지

- 본문 추출: `httpx`로 페이지를 가져와 `trafilatura`로 본문 텍스트 추출 (네이버 블로그는 iframe 내부 본문 주소로 다시 요청)
- LLM 구조화: LangChain + 기본 LLM 공급자(`langchain-openai`)로 본문 텍스트를 2.1 구조로 변환
  - 지시문: 본문에 적힌 내용만 사용, 수량은 원문 그대로, 없는 값은 비움, 레시피가 여러 개면 분리하고 주 요리·곁들임 관계 표시
  - 본문은 신뢰할 수 없는 데이터로 다루어 지시문과 구분해 전달하고, 본문 안의 지시는 따르지 않음
- 본문이 지나치게 길면 설정된 길이(`MAX_SOURCE_CHARS`)까지만 전달
- 본문 추출 실패(차단·동적 렌더링·본문 없음) → 수집 실패, 원본 URL 보존

## 5. 레시피 분리 및 곁들임 관계 분석

한 출처에서 레시피가 2개 이상 나온 경우에 적용한다 (모든 출처 공통).

### 5.1 분리

- `recipes[]`의 각 항목을 **별도 레시피**로 저장한다. 모든 레시피는 같은 출처(`source_id`)를 가리키고, 출처 안의 순번(`source_order`)으로 구분한다.
- 수집 시작 시 만든 대표 레시피(`importing`)에는 첫 번째 레시피를 채우고, 나머지는 새 레시피로 생성한다.
- 레시피명이 없으면 `"{출처 제목 또는 대표 레시피명} ({순번})"` 형태로 임시 표기하고 `uncertainFields`에 `title` 추가
- 같은 출처 안에서 레시피명이 같으면 뒤 레시피에 순번을 붙여 구분

### 5.2 주 요리·곁들임 판단

- 분석 결과의 `role`, `sideOf`를 근거로 한다. 별도 LLM 호출 없이 3.1·4.2의 같은 호출에서 함께 받는다.
- 판단 기준 (지시문)
  - 영상·본문에서 "곁들여", "함께 먹는", "반찬으로" 등으로 소개되거나, 주 요리와 함께 차려 내는 레시피 → `side`
  - 한 끼의 중심이 되는 요리 → `main`
  - 각각 독립된 요리 모음(예: "반찬 5가지")처럼 관계가 없으면 모두 `unknown` 또는 각자의 역할만 표시하고 `sideOf`는 비움
- `role = side`이고 `category`가 비어 있으면 `category = side`로 채운다.

### 5.3 곁들임 연결 생성

- `sideOf`에 지정된 주 요리와의 관계를 **사용자 지정 곁들임**(`recipe_side_dishes`: 주 요리 → 곁들임)으로 저장한다.
- 검증
  - `sideOf`의 순번이 실제 레시피 범위 안이고, 자기 자신이 아니며, 대상의 `role`이 `side`가 아닐 것
  - 조건을 벗어난 관계는 버린다 (레시피 저장은 계속 진행)
- 연결은 같은 출처에서 분리된 레시피끼리만 만든다. 사용자의 다른 레시피와는 자동으로 연결하지 않는다.
- 사용자는 레시피 상세의 `곁들임 레시피 연결`에서 자동 생성된 연결을 해제할 수 있다.
- 식단 추천은 `saved` 레시피만 사용하므로, 연결이 있어도 두 레시피 모두 사용자가 확인 처리해야 추천에 쓰인다.

## 6. 재료·단위 정리 (단위 환산)

LLM이 추출한 재료 목록을 레시피별로 저장 가능한 형태로 바꾸는 결정론적 단계다. 규칙 상세는 `./UNIT_CONVERSION.md`.

| 순서 | 처리 | 결과 |
|---|---|---|
| 1 | 재료명 정리: 앞뒤 공백·연속 공백 제거 | `normalized_name` |
| 2 | 재료 마스터 매칭: `normalized_name`이 같은 재료가 있으면 연결, 없으면 새로 생성 | `ingredient_id` |
| 3 | 원문 수량 보존 | `raw_amount` (예: `"1숟갈"`) |
| 4 | 수량 파싱: 숫자·분수·범위 해석 | `quantity` (예: `1`) |
| 5 | 단위 정규화: 별칭 사전으로 단위 코드 매칭 | `unit_code` (예: `tbsp`) |

- 4·5단계에서 해석하지 못하면 `quantity`·`unit_code`를 `null`로 두고 `raw_amount`만 남긴다. 해당 재료가 하나라도 있으면 그 레시피의 `uncertainFields`에 `ingredients` 추가
- 이 단계에서 인분 환산이나 단위 간 환산은 하지 않는다 (레시피 기준 수량 그대로 저장)

## 7. 결과 검증

- Pydantic 스키마 검증 (필드 타입·필수 구조)
- 도메인 검증 (레시피별)
  - `baseServings`, `cookMinutes`는 1 이상 정수일 때만 저장, 아니면 `null` + `uncertainFields`
  - 재료가 0개면 `uncertainFields`에 `ingredients`, 조리 순서가 0개면 `steps`
  - `category`가 허용 값이 아니면 `null`
  - 곁들임 관계 검증은 5.3
- 검증 실패는 수집 실패로 처리하지 않고, 해당 필드를 미확인으로 두어 사용자가 검토 단계에서 보완

## 8. 결과 반영

- job에 분석 결과 원본(`result`)과 완료 시각 저장
- 출처 분석 job(`import`, `retry`)은 **해당 출처의 가장 최신 job일 때만** 반영 (늦게 끝난 이전 job은 이력으로만 남김)
- 수정 요청 job(`revision`)은 **대상 레시피의 가장 최신 수정 요청 job일 때만** 반영
- 레시피 생성·갱신, 재료 연결, 조리 순서, 곁들임 연결을 **하나의 트랜잭션**으로 저장
- 모든 레시피의 상태를 `needs_review`로 두고, 사용자가 레시피별로 확인 처리하면 `saved`

## 9. 재시도와 수정 요청

출처 분석과 수정 요청을 구분한다.

| 구분 | 언제 | 출처 접속 | 처리 단위 |
|---|---|---|---|
| 출처 재분석 (9.1) | 레시피를 하나도 추출하지 못한 **완전 실패** (`status = failed`) | 함 (3·4장 다시 수행) | 출처 |
| 수정 요청 (9.2) | 레시피가 추출된 뒤 (`status = needs_review`) | **하지 않음** | 레시피 1개 |

### 9.1 출처 재분석 (완전 실패 시에만)

- 대상: 영상 분석 불가, 본문 추출 실패, 레시피 없음, 공급자 오류 등으로 레시피가 하나도 만들어지지 않은 경우
- `재시도`는 같은 출처를 3·4장부터 다시 분석한다 (`job_type=retry`).
- 완전 실패 상태에서 남긴 수정 요청은 코멘트를 지시문에 추가한 출처 재분석으로 처리한다 (수정할 레시피 데이터가 없으므로).
- 결과는 8장 규칙대로 반영하고, 레시피가 여러 개면 5장대로 분리한다.

### 9.2 수정 요청 (레시피 단위, 출처 접속 없음)

- 레시피가 분리된 상태면 **레시피마다 따로** 수정 요청한다. 한 번의 요청은 레시피 1개에만 적용된다.
- 코멘트는 화면에서 선택 입력으로 유지한다. 다만 출처에 접속하지 않으므로 코멘트가 비어 있으면 고칠 근거가 없다.
  - 코멘트가 비어 있으면 LLM을 호출하지 않고 검증 오류로 응답한다 (구현: `pipeline.revise_recipe`가 `ValueError`, API 계층에서 검증 오류로 변환).
  - 레시피·job은 바꾸거나 만들지 않는다.
  - `수집 실패` 상태(9.1)는 코멘트가 비어 있어도 출처 재분석을 진행한다.
- 입력: 대상 레시피의 현재 저장 데이터(레시피명, 카테고리, 기준 인분, 조리 시간, 재료명·원문 수량, 조리 순서, 미확인 필드) + 사용자 코멘트
- 처리: 기본 LLM 공급자(LangChain)로 코멘트가 가리키는 부분만 고친 레시피 1개를 2.1 구조(단일 레시피)로 받는다.
  - 지시문: 코멘트에 언급되지 않은 값은 그대로 유지, 코멘트에 근거가 없는 값을 새로 만들지 않음, 수량은 원문 표기로 기록
  - 코멘트는 신뢰할 수 없는 사용자 입력으로 구분해 전달하고, 레시피 수정과 무관한 지시는 따르지 않음
- 출처(영상·웹페이지·댓글)에는 다시 접속하지 않는다. Gemini·YouTube Data API·본문 수집을 호출하지 않는다.
- 결과는 6·7장(재료·단위 정리, 검증)을 거쳐 **대상 레시피만** 갱신하고 `needs_review`로 둔다.
- 같은 출처의 다른 레시피와 곁들임 연결은 바꾸지 않는다. 곁들임 연결 변경은 레시피 상세의 `곁들임 레시피 연결`에서 한다.
- job은 `job_type=revision`, `target_recipe_id`를 지정해 이력으로 남긴다.
- 레시피 합치기·누락 레시피 추가처럼 분리 결과 자체를 바꾸는 요청은 지원하지 않는다.

## 10. 설정값

| 키 | 용도 |
|---|---|
| `GEMINI_API_KEY`, `GEMINI_MODEL` | 유튜브 영상 분석 |
| `YOUTUBE_API_KEY` | 댓글 조회 |
| `LLM_PROVIDER`, `LLM_MODEL`, `OPENAI_API_KEY` | 웹 본문 구조화, 댓글 분석, 수정 요청 재정리 |
| `LLM_REASONING_EFFORT` | 텍스트 모델 thinking effort (기본 `none`). `none`일 때만 `temperature=0`을 적용하고, 그 외 값은 모델 기본 temperature 사용 |
| `AI_TIMEOUT_SECONDS`, `AI_MAX_RETRIES` | 공통 타임아웃·재시도 |
| `MAX_SOURCE_CHARS` | LLM에 전달할 본문 최대 길이 |
| `YOUTUBE_COMMENT_COUNT` | 댓글 조회 개수 (기본 3) |
| `MAX_RECIPES_PER_SOURCE` | 한 출처에서 분리할 최대 레시피 수 (초과분은 저장하지 않고 job 결과에만 기록) |

## 11. 결정 사항

| 항목 | 결정 |
|---|---|
| 분리된 레시피 수정 | 레시피별로 수정 요청, 출처에 접속하지 않고 저장 데이터 + 코멘트로 재정리 |
| 출처 재분석 | 레시피를 하나도 추출하지 못한 완전 실패 시에만 |
| 분리 결과 변경 (합치기·추가) | 지원하지 않음 |
| 댓글 분석 모델 | 기본 LLM 공급자 |
| 댓글 보완 병합 | 영상 값은 유지. 재료는 없는 재료 추가·빈 수량 채우기만, 조리 순서는 영상에 단계가 없을 때만 사용 (§3.3) |
