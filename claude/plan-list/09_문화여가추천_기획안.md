# [기획안 09] 취향 학습형 서울 문화·여가 활동 추천 서비스

> 개발 조건: 수업 실습 프로젝트, 무료 공개 데이터만 사용, 서울 한정, 카카오맵 API 확보, 백엔드 Python FastAPI

## 1. 개요
- **프로젝트명**: 취향 학습형 서울 문화·여가 활동 추천 서비스
- **추진 배경**
  - 서울에는 공연, 전시, 축제, 강좌, 체험 프로그램이 많지만 정보가 여러 포털에 흩어져 있고, 대부분 날짜·분류 기준 목록이라 개인 취향에 맞는 활동을 찾기 어려움
  - 무료·저비용 공공 프로그램은 접수 기간이 짧아 놓치기 쉬움
- **목적**: 사용자의 관심 분야, 가능한 시간, 예산, 동반 유형을 바탕으로 서울 문화·여가 활동을 추천하고, 사용자 반응(좋아요·관심 없음)으로 취향을 학습하여 추천을 개선
- **타겟 사용자**: 주말·퇴근 후 여가 활동을 찾는 서울 시민, 아이 동반 가족
- **범위**
  - 대상 활동: 서울시 문화행사, 서울시 공공서비스예약 문화체험·교육강좌, 서울 소재 공연(KOPIS)
  - 예매·예약은 원래 사이트로 연결
- **기존 서비스와의 차별점**
  - 여러 출처의 활동을 하나로 통합하고 개인 취향 점수로 정렬
  - 반응이 쌓일수록 추천이 바뀌는 학습 구조와 추천 이유 표시
  - "이번 주말 플랜": 시간이 겹치지 않고 동선이 가까운 활동 2~3개 묶음 제안

## 2. 주요 기능
1. **취향 온보딩**
   - 처음 접속 시 분야 카드(클래식, 뮤지컬, 전시, 축제, 공예 체험, 어린이 등) 중 관심 항목 선택
   - 가능한 요일·시간대, 선호 지역(자치구), 예산(무료만·3만 원 이하·무관), 동반 유형(혼자·친구·가족·아이 동반) 설정
2. **맞춤 추천 피드**
   - 조건에 맞는 활동을 취향 점수 순으로 표시
   - 각 카드에 추천 이유 표시 (예: "관심 분야 전시, 무료, 선호 지역 마포구")
   - 카드마다 좋아요·관심 없음 버튼, 상세 보기
3. **이번 주말 플랜**
   - 토·일 각각 시간이 겹치지 않고 장소 간 거리가 가까운 활동 2~3개 묶음 제안
   - 플랜의 장소를 카카오맵에 순서대로 표시
4. **지도 탐색**
   - 현재 위치 또는 선호 지역 기준으로 추천 활동 마커 표시, 거리순 정렬
5. **접수·마감 알림**
   - 관심 표시한 예약형 프로그램의 접수 시작·마감 일정 표시
   - 페이지가 열려 있을 때 접수 시작 알림, 캘린더 파일(.ics) 내보내기
6. **취향 프로필 보기**
   - 학습된 관심 분야 비중을 막대 차트로 표시, 사용자가 직접 조정·초기화 가능

- **확인 필요 사항**
  - KOPIS Open API 인증키 발급 절차, 일일 호출 한도, 지역(서울) 필터 파라미터
  - 공공서비스예약 정보의 문화체험·교육강좌 데이터셋 구분과 예약 상태 필드
  - 출처 간 같은 행사 중복 여부 (서울문화포털과 KOPIS 공연)

## 4. 추천 로직 설계
- **활동 표현 (서버, 수집 시)**
  - 공통 스키마로 통합: 제목, 분류, 기간·시간, 장소, 좌표, 요금, 대상, 출처, URL
  - 분류 체계 통일: 출처별 분류를 내부 분야 12종으로 매핑
  - 특징 벡터 = 분야 원-핫 + 제목·설명 키워드 TF-IDF + 속성(무료, 아이 동반 적합, 예약 필요)
  - 아이 동반 적합: 대상 연령 텍스트에서 "어린이", "가족", "전체관람가" 등 키워드 추출
- **사용자 취향 벡터 (브라우저)**
  - 초기값: 온보딩에서 선택한 분야
  - 갱신(로키오 방식): 좋아요 +1.0, 상세 보기 +0.3, 관심 없음 −0.7을 해당 활동 특징 벡터에 곱해 더함
  - 오래된 반응은 주 단위로 0.9배 감쇠하여 최근 취향 반영
- **후보 필터**
  - 기간: 오늘~4주 이내 진행 또는 접수 중
  - 사용자 조건: 가능한 요일·시간대, 예산, 선호 지역 또는 거리, 동반 유형
  - 이미 "관심 없음" 표시한 활동 제외
- **점수와 재정렬**
  - 기본 점수 = 취향 벡터와 활동 특징 벡터의 코사인 유사도
  - 가산: 접수 마감 7일 이내, 무료 선호 사용자의 무료 활동
  - 다양성 재정렬(MMR): 이미 고른 활동과 비슷한 활동은 감점하여 한 분야로 쏠리지 않게 함 (λ = 0.7)
- **이번 주말 플랜**
  - 주말 진행 활동 중 상위 20개 후보에서 시작 시간이 빠른 순으로 선택
  - 다음 활동은 앞 활동 종료 후 이동 시간(직선 거리 ÷ 대중교통 평균 속도 근사)을 고려하여 시작 가능한 활동 중 점수가 높은 것 선택
- **평가 지표**
  - 추천 상위 5개 중 좋아요 비율 (precision@5)
  - 학습 전(온보딩만)과 학습 후(반응 20개 이상) 비교

## 5. 개인정보 보호 설계
- **로그인 없음**: 취향 벡터, 반응 기록, 조건 설정은 브라우저(localStorage)에만 저장
- **서버 전송 최소화**: 추천 요청 시 사용자 식별자 없이 취향 벡터와 필터 조건만 전송. 서버는 요청 내용을 저장하지 않음
- **위치**: 현재 위치는 거리 계산에만 사용하고 저장하지 않음. 위치 대신 선호 자치구 선택 가능
- **사용자 통제**: 취향 프로필 직접 조정·초기화, 기록 내보내기·가져오기(JSON)

## 6. 시스템 아키텍처 및 기술 스택
- **Frontend**
  - HTML5, CSS3, JavaScript (ES6+)
  - 취향 벡터 갱신 모듈 (JavaScript), localStorage, Notification API
  - Kakao Maps JavaScript SDK (Marker, Polyline, services 라이브러리)
  - Chart.js (취향 프로필 차트)
- **Backend**
  - Python FastAPI (추천, 주말 플랜, 활동 상세 API)
  - SQLite (통합 활동 데이터, 특징 벡터)
  - APScheduler (출처별 데이터 일 1회 수집)
- **Data Processing**
  - Pandas (출처 통합, 분류 매핑, 중복 제거)
  - scikit-learn (TF-IDF 벡터화, 코사인 유사도)
  - 한국어 키워드 추출 (명사 위주 토큰화, 불용어 목록)
- **데이터 흐름**
  - 수집: 출처별 API → 공통 스키마 변환 → 중복 제거 → 특징 벡터 계산 → SQLite
  - 추천: 브라우저 취향 벡터·조건 전송 → 서버 필터·점수·재정렬 → 상위 활동과 추천 이유 반환 → 브라우저 반응 기록 → 취향 벡터 갱신

## 7. 개발 단계별 워크플로우

```
[1단계: 요구사항 정의 및 데이터 소스 식별]
  └─ 서울 열린데이터광장 인증키, KOPIS 인증키 발급, 카카오 도메인 등록
  └─ FastAPI 기초 실습

[2단계: 데이터 수집 및 통합]
  └─ 문화행사·공공서비스예약·KOPIS 데이터 수집, 공통 스키마 변환
  └─ 내부 분야 12종 매핑표, 제목·장소·날짜 기준 중복 제거
  └─ 좌표 없는 장소는 카카오 Geocoder·Places로 보완

[3단계: 특징 벡터 및 추천 로직]  ※ 핵심 단계
  └─ TF-IDF·속성 특징 벡터 생성, 아이 동반 적합 키워드 추출
  └─ 후보 필터, 코사인 점수, 가산, MMR 재정렬, 주말 플랜 선택 알고리즘
  └─ 취향 벡터 갱신 규칙 (브라우저 모듈), 가상 사용자 시뮬레이션 테스트

[4단계: 백엔드 API 구축]
  └─ 추천, 주말 플랜, 활동 상세 엔드포인트, 추천 이유 생성
  └─ 일 1회 수집 작업, 종료된 활동 정리

[5단계: 프론트엔드 및 지도 연동]
  └─ 온보딩, 추천 피드(좋아요·관심 없음), 주말 플랜 지도·동선
  └─ 접수 알림, .ics 내보내기, 취향 프로필 차트

[6단계: 통합 테스트 및 검증]
  └─ 팀원·지인 10명 2주 사용, precision@5 학습 전후 비교
  └─ 추천 다양성(상위 10개의 분야 수) 확인
  └─ 요청에 식별 정보가 포함되지 않는지 확인
```

## 8. 기대 효과 및 한계
- **기대 효과**
  - 흩어진 서울 문화·여가 정보를 개인 조건과 취향 기준으로 한 번에 탐색
  - 사용할수록 정확해지는 추천과 투명한 추천 이유
  - 짧은 접수 기간의 공공 프로그램 참여 기회 확대
- **한계**
  - 초기 사용자는 반응 데이터가 적어 추천이 온보딩 선택에 크게 의존
  - 활동 설명 텍스트의 품질과 길이가 출처마다 달라 특징 벡터 품질에 편차
  - 실시간 잔여 좌석·예약 가능 여부는 원 사이트에서 확인 필요
